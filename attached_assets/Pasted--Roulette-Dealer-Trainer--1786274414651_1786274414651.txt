Продолжаем развитие Roulette Dealer Trainer.

Сейчас уже работает полный запуск аттестации:

Создана аттестация
→ создан отдельный RouletteExercise для дилера
→ дилер видит аттестацию
→ нажимает `Начать аттестацию`
→ запускается существующая Spin-анимация и звук шарика
→ загружается заранее сохранённый RouletteExercise
→ TrainingAssignment переходит в `IN_PROGRESS`
→ дилер проходит существующий блок вопросов Roulette.

Следующий этап:

# Сохранение ответов и завершение аттестации

Нужно связать существующий механизм вопросов Roulette с TrainingAssignment и сохранить итог прохождения.

ВАЖНО:

не создавать новую независимую систему вопросов.

Существующая логика вопросов Roulette является источником истины.

---

# 1. Сначала проанализировать существующие вопросы

Перед изменениями найти текущую реализацию вопросов после Spin.

Определить:

* где создаётся последовательность вопросов;
* какие типы вопросов существуют;
* где хранится текущий вопрос;
* где хранится ответ пользователя;
* как определяется правильный ответ;
* как проверяется введённое значение;
* где фиксируется правильный/неправильный ответ;
* как сейчас формируется отчёт;
* что происходит после последнего вопроса;
* какие данные используются для вывода правильного расчёта и примера ошибки.

Особенно важно сохранить существующую последовательность вопросов.

Не менять правила расчётов.

---

# 2. В режиме PRACTICE ничего не менять

Обычный Roulette должен продолжать работать как сейчас.

То есть:

```text
Spin
→ вопросы
→ проверка
→ существующий результат/отчёт
```

Новый механизм сохранения аттестации должен включаться только если Roulette работает в:

`ATTESTATION`

режиме.

---

# 3. В режиме ATTESTATION сохранять ответы

При ответе дилера на каждый вопрос необходимо собрать данные для будущего результата.

Не нужно сразу менять TrainingAssignment на COMPLETED после каждого ответа.

Пока дилер отвечает:

`TrainingAssignment.status = IN_PROGRESS`.

---

# 4. Модель результата

Создать отдельную сущность:

`TrainingResult`

Концептуально:

```ts
type TrainingResult = {
  id: string;
  assignmentId: string;

  answers: TrainingAnswer[];

  totalQuestions: number;
  correctAnswers: number;

  createdAt: string;
  completedAt: string;
};
```

Если структура проекта требует немного другой формат — адаптировать.

Главное:

TrainingResult принадлежит конкретному TrainingAssignment.

---

# 5. Модель ответа

Не придумывай поля до анализа существующего question model.

Но сохранённого ответа должно быть достаточно, чтобы позже руководитель мог увидеть:

* какой вопрос был задан;
* что ответил дилер;
* какой ответ правильный;
* был ли ответ правильным.

Концептуально это может выглядеть:

```ts
type TrainingAnswer = {
  questionId: string;

  questionText: string;

  dealerAnswer: string | number;

  correctAnswer: string | number;

  correct: boolean;
};
```

Если существующие вопросы уже содержат подходящие id/type/title — переиспользовать их.

---

# 6. Сохранять тип вопроса

Если в Roulette существуют разные категории вопросов, желательно сохранять также существующий тип вопроса.

Например:

```ts
questionType
```

Но не создавать новую классификацию вручную.

Использовать реальные типы существующей Roulette.

Это понадобится позже руководителю для анализа ошибок.

---

# 7. Сохранять существующую проверку

Очень важно:

НЕ делать новую проверку вроде:

```ts
dealerAnswer === correctAnswer
```

если существующая Roulette уже имеет отдельные правила округления, кратности, числовой проверки и т.д.

Для определения:

`correct: true/false`

нужно использовать результат существующей логики проверки вопроса.

---

# 8. Не пересчитывать правильный ответ отдельно

Если существующий вопрос уже знает правильный ответ или вычисленный результат — использовать его.

Не создавать вторую независимую систему вычислений.

Иначе обычный Roulette и аттестация могут начать считать ответы по-разному.

---

# 9. Один Assignment — один Result

На текущем этапе действует правило:

```text
1 TrainingAssignment
=
1 RouletteExercise
=
1 TrainingResult
```

Повторных попыток пока нет.

Для одного Assignment нельзя создать два финальных результата.

---

# 10. Пока результат создаётся только при завершении

Во время прохождения ответы можно держать в состоянии аттестации.

Финальный `TrainingResult` создать после успешного прохождения всех обязательных вопросов.

Если уже удобно сохранять draft — это будет следующим отдельным этапом.

Сейчас главное — корректно сохранить финальный результат.

---

# 11. Последний вопрос

После ответа на последний обязательный вопрос в режиме ATTESTATION дилеру нужно дать действие:

`Завершить аттестацию`

Не завершать её автоматически до того, как последняя проверка закончена.

Пример:

```text
Вопрос 10 из 10

[ ответ ]

[ Проверить ]

...

Все вопросы пройдены.

[ Завершить аттестацию ]
```

Если существующий UI уже имеет подходящую финальную кнопку — переиспользовать её.

---

# 12. Завершение аттестации

После нажатия:

`Завершить аттестацию`

выполнить:

```text
1. проверить Assignment
2. проверить ownership currentDealerId
3. убедиться, что Assignment = IN_PROGRESS
4. убедиться, что все обязательные вопросы завершены
5. сформировать TrainingResult
6. сохранить TrainingResult
7. TrainingAssignment → COMPLETED
8. записать completedAt
9. открыть страницу результата
```

---

# 13. completedAt

Расширить TrainingAssignment, если ещё не сделано:

```ts
completedAt?: string;
```

Хранить полный timestamp.

В UI показывать:

`DD.MM.YYYY HH:mm`

без секунд.

---

# 14. startedAt не менять

После завершения Assignment должен иметь:

```text
createdAt
startedAt
completedAt
```

При завершении нельзя переписывать `startedAt`.

---

# 15. Подсчёт результата

Если каждый существующий вопрос имеет бинарный результат:

```text
правильно / неправильно
```

тогда:

```ts
totalQuestions = answers.length
correctAnswers = answers.filter(answer => answer.correct).length
```

Процент:

```text
correctAnswers / totalQuestions × 100
```

Округлить до целого процента для отображения.

Например:

```text
8 из 10
80%
```

---

# 16. Не вводить проходной балл

Пока НЕ создавать:

```text
PASSED
FAILED
```

Не добавлять:

* минимальный процент;
* сдал/не сдал;
* пересдачу.

Сейчас результат только фактический.

---

# 17. TrainingAssignment status

После успешного сохранения TrainingResult:

```text
IN_PROGRESS
→
COMPLETED
```

Нельзя сначала ставить COMPLETED, а потом пытаться сохранить Result.

Правильнее:

```text
сформировать result
↓
сохранить result
↓
обновить Assignment
```

---

# 18. Storage

Пока использовать localStorage.

Создать отдельный storage, например:

```text
roulette-trainer-training-results
```

или naming проекта.

Не сохранять результат:

* внутри Dealer;
* внутри TrainingTemplate;
* внутри RouletteExercise.

---

# 19. Минимальный storage API

Например:

```ts
getTrainingResults()

getTrainingResultByAssignmentId(
  assignmentId
)

addTrainingResult(
  result
)
```

Не создавать сложный repository framework.

---

# 20. Защита от двойного завершения

Если TrainingResult для assignmentId уже существует:

не создавать второй.

Если Assignment уже COMPLETED:

повторное нажатие завершения не должно создавать новый Result.

---

# 21. Экран результата

После завершения перейти на:

`/dealer/attestations/:assignmentId/result`

Создать минимальную страницу.

Показать:

```text
Аттестация завершена

Игра:
Roulette

Начало:
09.08.2026 14:20

Завершение:
09.08.2026 14:34

Правильных ответов:
8 из 10

Результат:
80%

[ Вернуться в кабинет ]
```

---

# 22. Откуда брать начало

Начало:

`TrainingAssignment.startedAt`

Завершение:

`TrainingAssignment.completedAt`

Не использовать createdAt вместо startedAt.

---

# 23. COMPLETED в кабинете дилера

После завершения в:

`Мои аттестации`

должно отображаться:

```text
Roulette
Статус: Завершена

[ Посмотреть результат ]
```

Вместо:

`Продолжить аттестацию`.

---

# 24. Повторное прохождение запрещено

Если Assignment = COMPLETED:

не открывать `/play` для нового прохождения.

Если пользователь вручную открывает play URL, перенаправить на result или показать:

`Аттестация уже завершена.`

Новый RouletteExercise не создавать.

---

# 25. Result должен принадлежать текущему дилеру

При открытии:

`/dealer/attestations/:assignmentId/result`

проверить:

```text
assignment.dealerId === currentDealerId
```

Чужой результат не показывать.

---

# 26. Если COMPLETED, но Result отсутствует

В случае повреждённых данных:

```text
Assignment = COMPLETED
Result отсутствует
```

показать:

`Результат аттестации недоступен.`

Не генерировать искусственный результат.

---

# 27. Не менять RouletteExercise

При завершении:

RouletteExercise остаётся неизменным.

Не удалять и не обновлять:

* winningNumber;
* bets;
* questions source data.

Он является исходным заданием, по которому проходилась аттестация.

---

# 28. Не менять Spin-анимацию

Сделанная логика первого запуска должна сохраниться:

```text
CREATED
→ Начать
→ Spin animation + звук
→ вопросы
```

После COMPLETED повторного Spin быть не должно.

---

# 29. Существующий отчёт ошибок

Если обычная Roulette уже после ответа показывает:

* ошибку;
* правильный расчёт;
* пример;

не удалять и не менять этот функционал.

В режиме ATTESTATION он должен продолжать работать.

TrainingAnswer просто фиксирует результат этой существующей проверки.

---

# 30. Проверка одного дилера

Сценарий:

1. Иванов имеет CREATED.
2. Нажимает `Начать`.
3. Assignment → IN_PROGRESS.
4. Проигрывается Spin-анимация.
5. Появляется сохранённый RouletteExercise.
6. Иванов отвечает на все вопросы.
7. Некоторые правильно, некоторые неправильно.
8. Нажимает `Завершить аттестацию`.
9. Создаётся один TrainingResult.
10. Assignment → COMPLETED.
11. completedAt установлен.
12. startedAt не изменился.
13. Открывается result page.
14. Отображается корректное количество ответов.
15. Отображается процент.

---

# 31. Проверка refresh

После завершения обновить страницу.

Должны остаться:

* COMPLETED;
* startedAt;
* completedAt;
* TrainingResult;
* answers;
* итоговый процент.

Ничего повторно не считать через Spin.

---

# 32. Проверка двух дилеров

Одна аттестация:

```text
Иванов
Петров
```

Иванов завершил:

```text
Иванов → COMPLETED + Result A
Петров → CREATED
```

Result Иванова не должен влиять на Assignment/Exercise Петрова.

---

# 33. Проверка кабинета руководителя

После завершения дилером существующая страница руководителя должна как минимум уже показать:

```text
Иванов — Завершена
```

потому что используется общий TrainingAssignment.status.

Пока процент в кабинете руководителя выводить НЕ обязательно.

Это следующий этап.

---

# 34. Не делать пока

Не реализовывать сейчас:

* подробный результат руководителя;
* таблицу результатов всех дилеров;
* сохранение незавершённых ответов после refresh;
* пересдачу;
* несколько попыток;
* pass/fail;
* backend;
* настоящую авторизацию.

---

# 35. Regression PRACTICE

Обязательно проверить обычную Roulette.

Обычный Spin и вопросы должны работать без обязательного создания TrainingResult.

То есть storage результатов аттестаций используется только для ATTESTATION.

---

Кратко сообщи:

1. где находится существующая логика вопросов;
2. какие существующие типы были переиспользованы;
3. какая структура TrainingAnswer получилась;
4. какая структура TrainingResult получилась;
5. какой localStorage key используется;
6. как фиксируется правильность ответа;
7. как считается correctAnswers;
8. как считается процент;
9. когда Assignment переводится в COMPLETED;
10. как записывается completedAt;
11. какой маршрут результата используется;
12. как исключено повторное прохождение;
13. что происходит при COMPLETED без Result;
14. подтверждение, что RouletteExercise не меняется;
15. подтверждение, что PRACTICE режим работает как раньше.

Выполни только этот этап.

Не переходи самостоятельно к экрану результатов руководителя или сохранению промежуточного прогресса.
